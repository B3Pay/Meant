The interface_id a pack is checked against is the identity of its own fragment: the validator compiles binds.requires (or reads binds.abi, with the struct types of binds.eip712) and resolves every annotation against it. It is not the identity of any ledger or token. A ledger that matches has its own interface_id, and the pack is applied to the ledger's types. A contract profile is checked against its own binds in the same way; the two shipped here bind EIP-712 types and no function.

How a pack matches

A Candid pack applies to a canister whose service is a subtype of the fragment in binds.requires, with result variants allowed to be wider (D-019); an EVM pack applies to a contract that has every function of its binds.abi with the same selector, output types and kind of call, with no subtyping. A matched pack is applied to the service's own types, so a position the pack names that the service lacks is skipped (I_PACK_ANNOTATION_SKIPPED); the full rules are on Profiles, layers and binding.

An EVM pack may also carry EIP-712 messages (binds.eip712, spec §15.9). It still matches by its binds.abi, and its messages then join the contract's resolved form under messages. The contract profiles permit2 and dai-permit are not packs: no pack search tries them, and they apply when given as profiles (--profile, or profiles in resolveService).

WayWhat it does
--packsTries every pack in the packs directory and applies those that match; the others get I_PACK_NOT_MATCHED (info). A pack for the other kind of interface is skipped: the EVM packs are never tried on a .did, nor the ICRC packs on an ABI. The contract profiles in the same directory are not packs and are never tried.
--packs-dir <dir>The packs directory (default: the standard packs the package ships).
--profile pack.jsonApplies the pack as given: it must match, or the resolve fails with E_PACK_NOT_MATCHED. A contract profile, such as permit2.profile.json, is applied this way too.
loadPacks(dir?)Every *.profile.json of kind "pack" in a directory, sorted by file name; by default DEFAULT_PACKS_DIR, the shipped packs. Packs only: erc20, erc2612, icrc1 and icrc2, never the two contract profiles. Node entry.
STANDARD_PACKSThe same four packs as data, from @meantjs/profile/browser, for a bundle that cannot read files.

ERC-2612

EIP-712 messages are spec §15.9 (D-055), the first part of the EVM binding's phase 2: profiles, consent text for a signing request and an ERC-7730 file of the messages. Signing and checking signatures are not in it. See EVM contracts.

EIP-2612 permits on EVM chains: the signed Permit message that sets an ERC-20 allowance, and the permit function that submits one. Spec: EIP-2612. File: profile/packs/erc2612.profile.json. It applies to a token that has every function of its binds.abi with the same selector, outputs and kind of call, decimals() and symbol() included, since the amounts read them. A signing request matches Permit by its type hash, and its verifying contract is the token, so the query: refs are calls to that token. The pack binds no domain: each token's name and version are its own. fact (EIP-2612) "The deadline argument can be set to uint(-1) to create Permits that effectively never expire", so a deadline of 2256 − 1 reads Never.

Permit2

experimental Uniswap's Permit2, as a contract profile (kind: "contract", origin: "third_party"), not a pack. File: profile/packs/permit2.profile.json. It describes four messages and no function: the AllowanceTransfer messages PermitSingle and PermitBatch, which set allowances (approve), and the SignatureTransfer messages PermitTransferFrom and PermitBatchTransferFrom, which authorize one transfer (transfer irreversible). Each amount is in the token its message names (amount.token): a consumer supplies that token's decimals() and symbol(), and shows its address beside the symbol.

It is bound to the domain named Permit2, with no version, and to 0x0000…8BA3 on chains 1 and 42161, so a look-alike contract named "Permit2" gets none of these words (E_DEPLOYMENT). fact ERC-7730's own Permit2 example lists these deployments (spec §15.9); its other chains are open item O10. fact (Uniswap permit2, Allowance.sol and AllowanceTransfer.sol) "If the inputted expiration is 0, the allowance only lasts the duration of the block", so an expiration of 0 reads Only in the block it is used; an allowance of type(uint160).max is never decremented, so it reads Unlimited. Witness messages (PermitWitnessTransferFrom) are left out: each protocol adds its own witness type (open O9, on Open questions).

DAI permit

experimental DAI's permit on Ethereum mainnet, older than EIP-2612 and different from it, as a contract profile (origin: "third_party"). File: profile/packs/dai-permit.profile.json. Only the message is described: DAI's functions are ERC-20's, and the ERC-20 pack covers them. It is bound to the domain Dai Stablecoin version 1 and to 0x6B17…1d0F on chain 1 (fact MCD_DAI in the Sky chainlog, read 2026-10-28, as spec §15.9 records).

fact (MakerDAO dss/src/dai.sol, as spec §15.9 records) An expiry of 0 never expires, allowed sets the allowance to uint(-1) or 0, and PERMIT_TYPEHASH is 0xea2aa0a1be11a07ed86d755c93467f4f82362b452371d1ba94d1715123511acb, which the resolver's hash matches. So expiry reads Never at 0 (a label) and at 2256 − 1 (the threshold). DAI's Permit shares its name with EIP-2612's and not its type hash, and a request is matched by the hash. allowed reads through the template; a case-like reading of true and false is open item O12.
