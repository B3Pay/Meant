The interface_id a pack is checked against is the identity of its own fragment: the validator compiles binds.requires (or reads binds.abi, with the struct types of binds.eip712) and resolves every annotation against it. It is not the identity of any ledger or token. A ledger that matches has its own interface_id, and the pack is applied to the ledger's types. A contract profile is checked against its own binds in the same way; the five shipped here bind EIP-712 types and no function.

How a pack matches

A Candid pack applies to a canister whose service is a subtype of the fragment in binds.requires, with result variants allowed to be wider (D-019); an EVM pack applies to a contract that has every function of its binds.abi with the same selector, output types and kind of call, with no subtyping. A matched pack is applied to the service's own types, so a position the pack names that the service lacks is skipped (I_PACK_ANNOTATION_SKIPPED); the full rules are on Profiles, layers and binding.

An EVM pack may also carry EIP-712 messages (binds.eip712, spec §15.9). It still matches by its binds.abi, and its messages then join the contract's resolved form under messages. The contract profiles (permit2, dai-permit, usdc, usdc-base-sepolia and x402-exact-permit2) are not packs: no pack search tries them, and they apply when given as profiles (--profile, or profiles in resolveService).

What the packs grant

A grant names who may take tokens because of a call or a signature, how many and until when, as positions of its arguments (Tags). A wallet reads it with the consent functions and checks it against terms the person confirmed for one task (Confirm terms for a task). These are every grant the nine files carry, read from their effect annotations:

The token is the one an amount.token names (Permit2's and x402's), else the ledger or contract called. An amount at or above its tag's threshold is unlimited, and an end at or above its tag's threshold never ends. EIP-2612's deadline and DAI's expiry bound only when the signature may be used, so they are not ends: those allowances never end (spec §5.3). The other transfers and approvals carry no grant: icrc2_transfer_from and ERC-20's transferFrom; and Permit2's PermitBatch and PermitBatchTransferFrom, which grant several tokens while a grant covers one. A request without a grant is not covered by terms and needs its confirmation. A pack whose grant does not hold in the service it is applied to keeps its effect and loses the grant (I_PACK_ANNOTATION_SKIPPED); in the ledger and token runs below every grant holds, and the resolved forms carry them all.

Using the packs

On the command line, --packs tries every pack the package ships and applies those that match:

npx candid-profile resolve ledger.did --packs > ledger.resolved.json

On the ICRC ledger's own .did (release ledger-suite-icrc-2026-03-09, the copy in profile/packages/resolver/test/fixtures/ledger.did) it applies two packs and reports on stderr:

WayWhat it does
--packsTries every pack in the packs directory and applies those that match; the others get I_PACK_NOT_MATCHED (info). A pack for the other kind of interface is skipped: the EVM packs are never tried on a .did, nor the ICRC packs on an ABI. The contract profiles in the same directory are not packs and are never tried.
--packs-dir <dir>The packs directory (default: the standard packs the package ships).
--profile pack.jsonApplies the pack as given: it must match, or the resolve fails with E_PACK_NOT_MATCHED. A contract profile, such as permit2.profile.json, is applied this way too.
loadPacks(dir?)Every *.profile.json of kind "pack" in a directory, sorted by file name; by default DEFAULT_PACKS_DIR, the shipped packs. Packs only: erc20, erc2612, icrc1 and icrc2, never the five contract profiles. Node entry.
STANDARD_PACKSThe same four packs as data, from @meantjs/profile/browser, for a bundle that cannot read files.
@meantjs/profile/packs/*The nine files themselves, as a package export (./packs/* maps to the package's data/packs/*): the four packs, and the five contract profiles, such as @meantjs/profile/packs/permit2.profile.json and @meantjs/profile/packs/x402-exact-permit2.profile.json.
 
import { createSchemaValidator, loadPacks, resolveService } from "@meantjs/profile";
import { readFileSync } from "node:fs";

const validateSchema = await createSchemaValidator(); // the schema this package ships
const packs = await loadPacks(); // the packs it ships, never its contract profiles
packs.map((p) => p.doc.name); // ["erc20", "erc2612", "icrc1", "icrc2"]
const r = await resolveService({
  did: readFileSync("ledger.did", "utf8"),
  validateSchema,
  packs: packs.map(({ doc }) => ({ doc })), // tried; applied only if they match
});

import icrc1 from "@meantjs/profile/packs/icrc1.profile.json" with { type: "json" };
const validateSchema = await createSchemaValidator(schema);                            // a document, not a path
const r = await resolveService({ did, validateSchema, packs: [{ doc: icrc1 }] });

Permit2

experimental Uniswap's Permit2, as a contract profile (kind: "contract", origin: "third_party"), not a pack. File: profile/packs/permit2.profile.json. It describes four messages and no function: the AllowanceTransfer messages PermitSingle and PermitBatch, which set allowances (approve), and the SignatureTransfer messages PermitTransferFrom and PermitBatchTransferFrom, which authorize one transfer (transfer irreversible). Each amount is in the token its message names (amount.token): a consumer supplies that token's decimals() and symbol(), and shows its address beside the symbol.

It is bound to the domain named Permit2, with no version, and to 0x0000…8BA3 on chains 1, 8453, 42161 and 84532, so a look-alike contract named "Permit2" gets none of these words (E_DEPLOYMENT). fact ERC-7730's own Permit2 example lists chains 1 and 42161; Base and Base Sepolia (8453 and 84532) were added in 0.5.0 from Permit2's code and DOMAIN_SEPARATOR(), read on each chain on 2026-10-30, and Uniswap's deployments page (spec §15.9, D-058). Its other chains are open item O10. fact (Uniswap permit2, Allowance.sol and AllowanceTransfer.sol) "If the inputted expiration is 0, the allowance only lasts the duration of the block", so an expiration of 0 reads Only in the block it is used; an allowance of type(uint160).max is never decremented, so it reads Unlimited. Witness messages (PermitWitnessTransferFrom) are left out of this profile: each protocol adds its own witness type. x402's has a profile of its own, x402-exact-permit2, and any other is open (open O9, on Open questions).

x402 through Permit2

experimental x402's exact payment through Permit2, as a contract profile (origin: "third_party", D-058). File: profile/packs/x402-exact-permit2.profile.json. It describes one message, Permit2's PermitWitnessTransferFrom with x402's witness Witness(address to,uint256 validAfter), which x402 signs for a token without EIP-3009 (transfer irreversible). It is bound to Permit2's domain and deployments: the domain Permit2, with no version, and 0x0000…8BA3 on chains 1, 8453, 42161 and 84532. The amount is in the token the message names (permitted.token): a consumer supplies that token's decimals() and symbol(), and shows its address beside the symbol.

Permit2 lets the spender choose where the tokens go and never reads the witness, so the witness's to is the payee only when the spender is x402's proxy, 0x402085c248EeA27D92E8b30b2C58ed07f9E20001. The profile pins the spender to it (fixed, spec §15.4): a request with any other spender gets no text (E_FIXED), and the grant pays witness.to. fact (coinbase/x402 at 0e6e8c5, contracts/evm/src/x402BasePermit2Proxy.sol and x402ExactPermit2Proxy.sol, as spec §15.9 records) the proxy's settle sends exactly permitted.amount to witness.to and reverts while the block's time is before validAfter, so the text reads "Usable from". fact (read on chain on 2026-10-30) the proxy has the same code on the four chains, and its PERMIT2() is Permit2. x402's upto scheme signs another witness, so another type hash, and matches nothing.
