Two JSON documents carry the profile layer. The profile is what an author, a reviewer or a pack writes: annotations bound to an interface. The resolved form is what the resolver writes for consumers: one tree per method, with the effective tags at every position. Both are format version 0. The structure of the profile is profile/spec/profile-v0.schema.json; the resolved form is spec §10 and, for EVM contracts, §15.5 and §15.9. Excerpts below are the generated fixtures in profile/fixtures/, quoted unchanged apart from indentation.

grant, inside effect

Since 0.4.0 (spec §5.3, D-056), an effect of kind transfer or approve may carry grant in its args: who may take tokens because of the call, how many and until when, as relpaths into the method's arguments. The ICRC-2 pack's: 

{
  "at": "icrc2_approve",
  "tag": "effect",
  "args": {
    "kind": "approve",
    "irreversible": false,
    "grant": {
      "spender": "spender",
      "amount": "amount",
      "ends": [
        "expires_at"
      ]
    }
  }
},
Field of grantRequiredValue
spenderexactly one of spender and toa relpath: who may take the tokens through an allowance, or with a signature someone else submits
toexactly one of spender and toa relpath: who a transfer pays directly
amountyesa relpath to an amount-tagged position, or a bool
endsnoan array of 1–8 relpaths to timestamp-tagged positions

No other field is allowed (additionalProperties: false, the schema's grant definition), and the schema's oneOf takes exactly one of spender and to; anything else is E_SCHEMA. What the positions must be, and E_GRANT when they are not, is on Tags. A grant is part of its effect annotation, not an annotation of its own, so the validator's annotation counts do not include it; the profile's profile_id changes with it, as with any edit.

profile_id

A profile's identity is candid-profile:v0:sha256: and the SHA-256 of the RFC 8785 (JCS) canonical JSON of the whole document, in lowercase hex. Any edit changes it, a change to description included; reordering keys does not, because JCS sorts them. The validator prints it: 

cd profile
node scripts/validate.mjs packs/icrc1.profile.json

PASS packs/icrc1.profile.json  (0 error, 0 warning, 0 info)
     profile_id   candid-profile:v0:sha256:4eaa9312d60661248ff5627dba9906aa91240abe84cb1b1da8ca20a6fba2e3e6
     interface_id candid-core:interface:v1:sha256:7fae0dd330b20f53ae1e4e2cb1947c1c57791da0ae20299ceb499f63228d0689  [5 methods, 29 annotations]

@meantjs/profile exports the same computation, and the canonical JSON it hashes:

import { profileId, jcs } from "@meantjs/profile";
import { readFileSync } from "node:fs";

const doc = JSON.parse(readFileSync("packs/icrc1.profile.json", "utf8"));
profileId(doc); // "candid-profile:v0:sha256:4eaa9312…"
jcs({ b: 1, a: [true, "x"] }); // '{"a":[true,"x"],"b":1}'

A profile never changes interface_id or contract_id: it is a separate document bound to them. The resolved form's profiles list carries each applied profile's profile_id, so a consumer can say which document wrote the words it shows.

Tags and their provenance

Every tag carries where it came from: origin is the layer of the profile that supplied it, and profile that profile's name. The one tag with "origin": "default" and no profile is an effect the resolver supplied. This is the idempotency stamp of icrc1_transfer, which the tool layer fills and ui.hidden keeps out of forms:

Where a node's tags come from:

  • Tags from type: addresses appear at every position reached through that edge.
  • A method-address tag at the same position wins (§8). In the tokens example, type:Tokens.e8s gives every e8s the label Amount, and balance->(0).e8s overrides it with Balance in balance's result.
  • A case node's tags may hold intent and effect (D-053). A consumer that does not read them uses the method's.
  • A stale profile supplies no value-conversion tag; its other tags stay.
"e8s": {
  "candid": "nat64",
  "tags": {
    "amount": {
      "args": {
        "decimals": 8,
        "symbol": "TOK"
      },
      "origin": "author",
      "profile": "tokens-example"
    },
    "describe": {
      "args": {
        "label": "Balance"
      },
      "origin": "author",
      "profile": "tokens-example"
    }
  }
}

Ordering

  • Methods are sorted by name.
  • Record fields and variant cases follow canonical id order (the Candid field hash), not source order. icrc1_transfer's argument lists to, fee, memo, from_subaccount, created_at_time, amount. Use ui.order for presentation.
  • profiles is highest layer first.

Unresolved dynamic values

A dynamic value stays as written, { "from": "query:icrc1_decimals" }: resolving it needs the network, so it is the consumer's job. The packages take the resolved values as refs, keyed by their from ({ "query:icrc1_decimals": 8 }). An EVM amount whose token names its token by a field stays as that path too; the consumer reads the token's decimals and symbol and passes them per token address (tokens in @meantjs/consent/evm, token in formatterFor). open OQ-10 (owner W1/W3): should the resolved form carry resolved dynamic values with their provenance, certified or not?

EIP-712 messages
