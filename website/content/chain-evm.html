A profile can describe an EVM contract's functions. From it come consent text for a call's calldata and an ERC-7730 clear-signing file with its ERC-8176 descriptorHash. A profile can also describe the EIP-712 messages a wallet is asked to sign, with consent text for a signing request and an ERC-7730 file of the messages. Agent tools, outcome classes over reverts, idempotency by nonce and ERC-7730 import are later phases, each its own decision; signing, checking signatures and Permit2's witness messages are not in it. The preregistered eval uses none of it. Decisions D-054 and D-055; the text is spec §15 and its §15.9.

The same resolver reads an ABI where it would read a .did, so addresses, tags, layers and the resolved form work as they do for a canister. This resolves a token's ABI on a local chain with the standard packs, encodes a transfer, and turns the calldata into the text a person confirms: 

import { createSchemaValidator, loadPacks, resolveService } from "@meantjs/profile";
import { parseAbi, encodeCall } from "@meantjs/profile/evm";
import { evmConsent } from "@meantjs/consent/evm";

const abi = [
  "function symbol() view returns (string)",
  "function decimals() view returns (uint8)",
  "function balanceOf(address owner) view returns (uint256)",
  "function allowance(address owner, address spender) view returns (uint256)",
  "function transfer(address to, uint256 value) returns (bool)",
  "function approve(address spender, uint256 value) returns (bool)",
  "function transferFrom(address from, address to, uint256 value) returns (bool)",
];
const validateSchema = await createSchemaValidator();
const packs = (await loadPacks()).map(({ doc }) => ({ doc }));
const { resolved } = await resolveService({ abi, validateSchema, packs }); // the erc20 pack matches
if (resolved === null) throw new Error("the ABI cannot be read");

const transfer = parseAbi(abi).functions.find((f) => f.name === "transfer");
if (transfer === undefined) throw new Error("no transfer function");
const calldata = encodeCall(transfer, { to: "0x70997970c51812dc3a010c7d01b50e0d17dc79c8", value: "1500000" });

const consent = evmConsent({
  resolved,
  calldata,
  to: "0x5fbdb2315678afecb367f032d93f642f64180aa3", // the token, on a local Anvil chain
  chainId: 31337,
  refs: { "query:decimals": 6, "query:symbol": "TKA" }, // read by the caller with eth_call
});
console.log(consent.message);

The ABI as an interface

fact A function is matched by its selector, the first 4 bytes of Keccak-256 (Ethereum's, not NIST SHA3-256) of its type-only signature: transfer(address,uint256) is 0xa9059cbb. Parameter names are not part of it; ERC-7730 files carry them in their keys (transfer(address to,uint256 value)), and so does a profile, in binds.abi (ERC-7730).

  • binds.abi is an array of human-readable fragments (function transfer(address to, uint256 value) returns (bool)) or JSON ABI entries. Only functions are read: events, errors, the constructor, fallback and receive are skipped.
  • Aliases read as their canonical types (uint is uint256, constant is view). A function's canonical fragment is function NAME(type name,…) [view|pure|payable] returns (…).
  • Overloaded names are refused (E_ABI; open O1): an address names a function by its name alone.
ABIAs a profile sees it
a functiona method: view and pure are queries, nonpayable and payable updates
its parametersone record at argument index 0: transfer(0).to; a function without parameters has no argument
its outputsthe result tuple: balanceOf->(0)
a tuplea record, its components in ABI order. A named component's id is the Candid hash of its name; an unnamed one's is its position, addressed #i
T[], T[k]a vector, []; T[k] keeps its length
anything elsea primitive named by its canonical type: uint256, int64, address, bool, string, bytes, bytes32

Template placeholders read {to} and {value}, as ERC-7730's do. See Addresses.

Identity

An ABI's identity is candid-profile:evm-abi:v0:sha256:<hex>: SHA-256 over the RFC 8785 (JCS) form of the sorted canonical fragments. It is the resolved form's interface_id, and what a contract profile binds to. Because the fragments are sorted, the order of binds.abi does not move it. The ERC-20 pack's seven functions:

candid-profile:evm-abi:v0:sha256:81471b5efd3e34c464b5dda12ccdd454d8ca6e0d0c069871c8152bc6b154be4b

When the interface has EIP-712 types, the hash covers them with the functions: one more line per struct, struct <Name>(<type> <name>,…), sorted with the fragments. With no types it is the hash above, so a resolved form without messages keeps its id. A token whose ABI has ERC-20's functions and EIP-2612's permit, nonces and DOMAIN_SEPARATOR resolves to …6ad2a3fd… with the ERC-20 pack alone and to …c0cd422e… once the EIP-2612 pack adds its Permit type (both measured by resolving that ABI with @meantjs/profile 0.3.0). Whether a contract profile is rebound or stale is decided by its functions alone, so the messages a pack adds never make it stale.

Values

  • Integers are uintN and intN for N = 8, 16, …, 256, with the bounds of their N bits. amount input and display are the same as on a canister, with no rounding: E_EXCESS_PRECISION, never a rounded value.
  • Addresses have one text form, 0x and 40 hex digits, shown with their EIP-55 checksum. On input, an address in mixed case must match its checksum; an address in one case carries no checksum and is accepted (open O3).
  • Calldata is decoded strictly: bytes that are not the canonical ABI encoding of the values read (dirty padding, an offset that does not point where the encoder would write, bytes left over) are refused. The consent text re-encodes the values it read and compares the bytes.

How a recipient is written differs by chain:

An ICRC-1 account: the account tag reads the textual encoding (principal-checksum.subaccounthex, or a bare principal for the default subaccount) and verifies its checksum. See Internet Computer.

An address needs no tag. It is read as 0x and 40 hex digits and shown in its EIP-55 form, 0x7099…79C8. The account and subaccount tags do not apply (E_TAG_NOT_APPLICABLE).

Contract profiles and EVM packs

ERC-7730 files and ERC-8176 attestations

fact An ERC-8176 attestation is an EAS attestation, under the schema bytes32 descriptorHash (UID 0xe023eef1…b5c2), that a party reviewed the ERC-7730 file whose RFC 8785 serialization has that Keccak-256. It describes no call; it vouches for a file (ERC-8176, Draft).

erc7730Descriptor writes that file from an EVM contract's resolved form. The same resolved form always gives the same bytes, so the same descriptorHash. $schema names the exact version erc7730-v2.1.0.schema.json, so a new release of the v2 alias cannot move the hash. There is one entry per function a transaction calls (an update), keyed by its signature. The messages of the same resolved form are a file of their own, with context: "eip712" (below).

Typed messages (EIP-712)

fact A signing request (eth_signTypedData_v4) has types, primaryType, domain and message. The signature signs keccak256(0x1901 ‖ domainSeparator ‖ hashStruct(message)). A struct's typeHash is the Keccak-256 of its encodeType: the struct with its members, then every struct it refers to, sorted by name. The domain's fields are name, version, chainId, verifyingContract and salt, in that order, each optional, and a user agent should refuse to sign when chainId is not the active chain (EIP-712, Final).

A profile can describe those messages, so a wallet shows what a signature allows before the person signs it. This is the first part of phase 2 (D-055): consent text for a signing request and an ERC-7730 file of the messages. Signing, checking signatures, witness messages (O9) and agent tools are not in it. Types

  • binds.eip712 is { domain, types }, in a contract profile or an EVM pack. types has the request's own JSON shape, without EIP712Domain.
  • domain is optional and binds only the name and the version; chainId and verifyingContract come from binds.deployments. A pack has no domain, since each token's is its own, and keeps its binds.abi, by which it matches.
  • A struct name is an identifier that does not read as an ABI type (uint256, bytes32, tuple, …) and is not EIP712Domain. Members have unique names.
  • A member type is a canonical ABI type as written, uint256 and never uint, because the type hash hashes the text; or a struct of the same map. Either may have array suffixes, T[] or T[k] with k ≥ 1. No struct contains itself.
  • Anything else is E_EIP712 at its place, and a struct that refers to a refused one is refused too.

Messages

  • A message is a type the same document tags with intent at its bare name (Payout). Its struct is argument 0, as a function's parameters are: Payout(0).legs[].amount, PermitSingle(0).details.amount.
  • A type without an intent is a type only. An address that names it is E_ADDR_UNRESOLVED; Leg above is described inside Payout.
  • A message may not share its name with a function, and two profiles may not give one type name different members (the later profile is invalid). Types with no message and no function describe nothing. Each is E_EIP712.

Matched by type hash, never by name

The resolver computes each message's encode_type and type_hash, and a request is matched to a message by its type hash. DAI's Permit and EIP-2612's share a name and not a hash, so neither profile's words can describe the other's signature:

Tags on a message

  • intent and effect work as on a function. A signature runs nothing when it is signed, so effect says what it allows, of any kind: approve for an allowance, transfer for a one-time transfer. The default is write, irreversible.
  • replicated does not apply to a signature (E_EFFECT_MODE).
  • The value tags apply to a message's members as to a function's parameters (Tags on EVM), and the tags that are not defined for EVM yet are not defined here either.
  • The interface id covers the message types with the functions (Identity).

An amount in the token a field names

A Permit2 message names its token in a field, so the amount's decimals and symbol cannot be the contract's own. amount.token is a relative path from the argument to an address field of the same argument, whose path up to its last [] is the amount's own: the token is in the same array element as the amount, or outside every array. The payout above has "token": "legs[].token" for legs[].amount.

  • decimals and symbol are not given (the schema refuses them): they are that token's decimals() and symbol().
  • The consumer reads them and passes them per token address, as tokens; the libraries do no I/O. Without an entry there is no text (E_REF_UNRESOLVED), never a number read in the wrong decimals.
  • A token's symbol() is its own claim, so its address is always shown beside it: 1.5 TKA (0x5FbDB2315678afecb367f032d93F642f64180aa3).
  • A path that breaks these rules is E_TOKEN_PATH, such as "token": "deadline", a uint256. So is token on a Candid service, whose ledger a field cannot name yet (OQ-6).
  • token works on functions too, and evmConsent takes the same tokens.

Consent text for a signing request

eip712Consent in @meantjs/consent/evm takes the resolved form, the request as the wallet received it and the wallet's active chain. This is a token on a local Anvil chain with EIP-2612's permit: the ERC-20 and EIP-2612 packs both match its ABI, and the request asks Alice (0xf39F…2266) to let Bob (0x7099…79C8) spend 2.5 TKA. 

import { createSchemaValidator, loadPacks, resolveService } from "@meantjs/profile";
import { eip712Consent } from "@meantjs/consent/evm";

const abi = [
  "function symbol() view returns (string)",
  "function decimals() view returns (uint8)",
  "function balanceOf(address owner) view returns (uint256)",
  "function allowance(address owner, address spender) view returns (uint256)",
  "function transfer(address to, uint256 value) returns (bool)",
  "function approve(address spender, uint256 value) returns (bool)",
  "function transferFrom(address from, address to, uint256 value) returns (bool)",
  "function permit(address owner, address spender, uint256 value, uint256 deadline, uint8 v, bytes32 r, bytes32 s)",
  "function nonces(address owner) view returns (uint256)",
  "function DOMAIN_SEPARATOR() view returns (bytes32)",
];
const validateSchema = await createSchemaValidator();
const packs = (await loadPacks()).map(({ doc }) => ({ doc }));
const { resolved } = await resolveService({ abi, validateSchema, packs }); // erc20 and erc2612 apply
if (resolved === null) throw new Error("the ABI cannot be read");

const typedData = {
  types: {
    Permit: [
      { name: "owner", type: "address" },
      { name: "spender", type: "address" },

    ],
  },
  primaryType: "Permit",

# Permit token spending

Allow `0x70997970C51812dc3A010C7d01b50e0d17dc79C8` to spend up to `2.5 TKA` from `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`. Signature expires: `2027-01-01 00:00:00 UTC`.

- **Spender:** `0x70997970C51812dc3A010C7d01b50e0d17dc79C8`
- **Amount:** `2.5 TKA`
- **Owner:** `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`
- **Signature expires:** `2027-01-01 00:00:00 UTC`

**Contract:** `0x5FbDB2315678afecb367f032d93F642f64180aa3` on chain 31337

**EIP-712 digest:** `0xf5f7c7ab25ddf658e38e97e75f692da15053528f00300b959122fcdf74b593c4`

This is a signature, not a transaction: whoever holds it can submit it.

The text is the same model and the same two forms as a call's, then the verifying contract and its chain, the EIP-712 digest, and the note that a signature is not a transaction. A hardware wallet that shows the hash can be checked against the digest. With the result come primaryType, typeHash (here 0x6e71edae…26c9), digest, verifyingContract in its EIP-55 form, chainId, diagnostics, and provenance, here { origin: "pack", profile: "erc2612" } for the intent: the words come from a pack, not from the token.

The same request for an unlimited amount that never expires, value and deadline both uint256 max, in the fields form:

0x7099…79C8 Unlimited TKA 0xf39F…2266 Never 0x5FbD…0aa3 on chain 31337 This is a signature, not a transaction: whoever holds it can submit it 0x1ed6…d724

What is refused before anything is shown

  1. E_DOMAIN: a domain field EIP-712 does not define; a salt (O11); a types.EIP712Domain that does not list the domain's fields in EIP-712 order (it may be left out); no chainId, so the signature would be valid on every chain; no verifyingContract; a chainId other than the wallet's; a name or version other than that of every profile that binds a domain, absent where the profile's is absent (Permit2's domain has no version).
  2. E_TYPE_HASH: no message has the request's type hash. E_DEPLOYMENT: a profile lists deployments and the verifying contract on that chain is not one of them, so a look-alike contract named "Permit2" gets none of Permit2's words.
  3. E_DECODE: values that are not exactly the members, or not canonical. Integers are decimal strings without leading zeros, or JSON numbers up to 253 − 1, within their type's range. Addresses follow Values. bytesN has exactly N bytes, as 0x hex. An array has its declared length, within the decoder's limits.
  4. E_REF_UNRESOLVED: an amount in a token not in tokens, or a query: ref not in refs. For a pack's message the query: refs are calls to the verifying contract: resolve that contract's ABI with the packs, as above.

ERC-7730 files of messages

Local tests

The repository runs no EVM node: none of its tests starts Anvil or calls a deployed contract. What is tested runs in Node against fixed vectors:

  • Keccak-256 against an independent implementation (and the block boundary), the ERC-20 selectors, the ERC-8176 schema UID, EIP-55's examples and EIP-712's Mail example (profile/packages/resolver/test/evm.test.mjs).
  • Every exported ERC-7730 file in the consent tests is checked against the ERC-7730 2.1.0 JSON Schema (vendored, with its sha256), and the hashes and digests the tests pin were computed by an independent implementation.
  • EIP-712: encodeType and the type hash of EIP-712's Mail example, the types that are refused, the standard messages' type hashes, token paths and timestamp words (profile/packages/resolver/test/eip712.test.mjs); the consent text of Permit2, EIP-2612 and DAI requests and every refusal above (profile/packages/consent/test/eip712.test.mjs). No chain, no network, nothing signed.

A test against a contract would run on a local Anvil chain, as the examples on this page assume, never on mainnet.
