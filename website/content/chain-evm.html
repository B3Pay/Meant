A profile can describe an EVM contract's functions. From it come consent text for a call's calldata and an ERC-7730 clear-signing file with its ERC-8176 descriptorHash. Agent tools, outcome classes over reverts, idempotency by nonce, EIP-712 messages and ERC-7730 import are later phases, each its own decision. The preregistered eval uses none of it. Decision D-054; the text is spec §15.

The same resolver reads an ABI where it would read a .did, so addresses, tags, layers and the resolved form work as they do for a canister. This resolves a token's ABI on a local chain with the standard packs, encodes a transfer, and turns the calldata into the text a person confirms: 

import { createSchemaValidator, loadPacks, resolveService } from "@meantjs/profile";
import { parseAbi, encodeCall } from "@meantjs/profile/evm";
import { evmConsent } from "@meantjs/consent/evm";

const abi = [
  "function symbol() view returns (string)",
  "function decimals() view returns (uint8)",
  "function balanceOf(address owner) view returns (uint256)",
  "function allowance(address owner, address spender) view returns (uint256)",
  "function transfer(address to, uint256 value) returns (bool)",
  "function approve(address spender, uint256 value) returns (bool)",
  "function transferFrom(address from, address to, uint256 value) returns (bool)",
];
const validateSchema = await createSchemaValidator();
const packs = (await loadPacks()).map(({ doc }) => ({ doc }));
const { resolved } = await resolveService({ abi, validateSchema, packs }); // the erc20 pack matches
if (resolved === null) throw new Error("the ABI cannot be read");

const transfer = parseAbi(abi).functions.find((f) => f.name === "transfer");
if (transfer === undefined) throw new Error("no transfer function");
const calldata = encodeCall(transfer, { to: "0x70997970c51812dc3a010c7d01b50e0d17dc79c8", value: "1500000" });

const consent = evmConsent({
  resolved,
  calldata,
  to: "0x5fbdb2315678afecb367f032d93f642f64180aa3", // the token, on a local Anvil chain
  chainId: 31337,
  refs: { "query:decimals": 6, "query:symbol": "TKA" }, // read by the caller with eth_call
});
console.log(consent.message);

The ABI as an interface

fact A function is matched by its selector, the first 4 bytes of Keccak-256 (Ethereum's, not NIST SHA3-256) of its type-only signature: transfer(address,uint256) is 0xa9059cbb. Parameter names are not part of it; ERC-7730 files carry them in their keys (transfer(address to,uint256 value)), and so does a profile, in binds.abi (ERC-7730).

  • binds.abi is an array of human-readable fragments (function transfer(address to, uint256 value) returns (bool)) or JSON ABI entries. Only functions are read: events, errors, the constructor, fallback and receive are skipped.
  • Aliases read as their canonical types (uint is uint256, constant is view). A function's canonical fragment is function NAME(type name,…) [view|pure|payable] returns (…).
  • Overloaded names are refused (E_ABI; open O1): an address names a function by its name alone.
ABIAs a profile sees it
a functiona method: view and pure are queries, nonpayable and payable updates
its parametersone record at argument index 0: transfer(0).to; a function without parameters has no argument
its outputsthe result tuple: balanceOf->(0)
a tuplea record, its components in ABI order. A named component's id is the Candid hash of its name; an unnamed one's is its position, addressed #i
T[], T[k]a vector, []; T[k] keeps its length
anything elsea primitive named by its canonical type: uint256, int64, address, bool, string, bytes, bytes32

Template placeholders read {to} and {value}, as ERC-7730's do. See Addresses.

Identity

An ABI's identity is candid-profile:evm-abi:v0:sha256:<hex>: SHA-256 over the RFC 8785 (JCS) form of the sorted canonical fragments. It is the resolved form's interface_id, and what a contract profile binds to. Because the fragments are sorted, the order of binds.abi does not move it. The ERC-20 pack's seven functions:

candid-profile:evm-abi:v0:sha256:81471b5efd3e34c464b5dda12ccdd454d8ca6e0d0c069871c8152bc6b154be4b

Values

  • Integers are uintN and intN for N = 8, 16, …, 256, with the bounds of their N bits. amount input and display are the same as on a canister, with no rounding: E_EXCESS_PRECISION, never a rounded value.
  • Addresses have one text form, 0x and 40 hex digits, shown with their EIP-55 checksum. On input, an address in mixed case must match its checksum; an address in one case carries no checksum and is accepted (open O3).
  • Calldata is decoded strictly: bytes that are not the canonical ABI encoding of the values read (dirty padding, an offset that does not point where the encoder would write, bytes left over) are refused. The consent text re-encodes the values it read and compares the bytes.

How a recipient is written differs by chain:

An ICRC-1 account: the account tag reads the textual encoding (principal-checksum.subaccounthex, or a bare principal for the default subaccount) and verifies its checksum. See Internet Computer.

An address needs no tag. It is read as 0x and 40 hex digits and shown in its EIP-55 form, 0x7099…79C8. The account and subaccount tags do not apply (E_TAG_NOT_APPLICABLE).

Contract profiles and EVM packs

A contract profile has kind: "contract", an origin of author, third_party or inferred, its ABI in binds.abi and, optionally, the contracts it describes in binds.deployments, as ERC-7730's context.contract.deployments does. A mixed-case address that fails its EIP-55 checksum is E_ADDRESS_CHECKSUM; a deployment listed twice is W_DUPLICATE. An example, written for this page, for a token on a local chain:

  • A contract profile is checked against its own binds.abi. Resolved against another ABI (candid-profile resolve --abi), it is rebound or stale by the same rules as a canister profile.
  • An EVM pack has kind: "pack" and binds.abi instead of binds.requires. It applies to a contract that has every function of the pack with the same selector (so the same name and parameter types), the same output types and the same kind of call: a query, or an update that is payable exactly when the pack's is. There is no subtyping.
  • A pack's addresses and placeholders use the pack's parameter names; when it applies, they are rewritten to the contract's, component by component, by position. EIP-20 names them _to and _value, WETH dst and wad: on an ABI with transfer(address dst, uint256 wad), the ERC-20 pack's template reads Send {wad} to {dst}.
  • A profile or pack for the other kind of interface is E_CHAIN when given explicitly, and skipped in a pack search.
  • The standard pack is ERC-20: transfer, approve, transferFrom, balanceOf, allowance, decimals and symbol. fact decimals() and symbol() are optional in EIP-20, so a token without them matches no pack and needs a contract profile with literal values, like the one above.

A hostile contract can match ERC-20, call its drain "Send tokens" and answer "USDT" to symbol(). A consumer must show the contract's address, with its EIP-55 checksum, whenever it asks a person to confirm a call matched by a pack; the consent text ends with it. fact ERC-7730's Security Considerations name the same risk, "parameter injection using legitimate, high-profile contract formats". query: refs on an EVM contract are eth_calls answered by one RPC node. See Security model.

The resolved form: chain evm

An EVM contract's resolved form has "chain": "evm" at the top. Its nodes carry abi where a Candid form's carry candid: the canonical type of a primitive, "tuple" with fields, or "array" with element and, for T[k], length. Each method also has selector, signature and state_mutability, and each entry of profiles that binds deployments lists them. A consumer must refuse a resolved form whose chain it does not know rather than read it as Candid; @meantjs/consent (main entry) and @meantjs/tools do.

ERC-7730 files and ERC-8176 attestations

fact An ERC-8176 attestation is an EAS attestation, under the schema bytes32 descriptorHash (UID 0xe023eef1…b5c2), that a party reviewed the ERC-7730 file whose RFC 8785 serialization has that Keccak-256. It describes no call; it vouches for a file (ERC-8176, Draft).

erc7730Descriptor writes that file from an EVM contract's resolved form. The same resolved form always gives the same bytes, so the same descriptorHash. $schema names the exact version erc7730-v2.1.0.schema.json, so a new release of the v2 alias cannot move the hash. There is one entry per function a transaction calls (an update), keyed by its signature. 

import { erc7730Descriptor, erc8176Attestation } from "@meantjs/consent/erc7730";

const { descriptor, descriptorHash } = erc7730Descriptor(resolved, {
  deployments: [{ chainId: 31337, address: "0x5FbDB2315678afecb367f032d93F642f64180aa3" }],
});
const { typedData, digest } = erc8176Attestation({
  descriptorHash,
  time: 1777630591,
  expirationTime: 1785406591,
  salt: "0x" + "11".repeat(32), // 32 random bytes, chosen by the caller
});
// A reviewer signs `digest` with their own key. Nothing here signs or sends it.
console.log(descriptor.display.formats["transfer(address to,uint256 value)"], typedData.message.data);

What a profile says that an ERC-7730 file cannot say is refused (E_EXPORT), never written as something near it: a time in another unit, utf8 or base64 bytes, an amount whose decimals and symbol are not the contract's own, an unnamed parameter, a placeholder over an array or a whole tuple. effect and the agent tags have no ERC-7730 form: the file carries what a call says, not what it does.

erc8176Attestation gives the unsigned offchain attestation (EAS offchain v2 typed data: domain EAS Attestation, version 0.26, chain 1, the canonical EAS contract; data is the hash) and its EIP-712 digest. A reviewer signs it with their own key. This repository never signs or posts one: it holds no reviewer's key, and an onchain attestation spends mainnet ETH. Checking attestations is a later phase (open OQ-7, OQ-9).

Local tests

The repository runs no EVM node: none of its tests starts Anvil or calls a deployed contract. What is tested runs in Node against fixed vectors:

  • Keccak-256 against an independent implementation (and the block boundary), the ERC-20 selectors, the ERC-8176 schema UID, EIP-55's examples and EIP-712's Mail example (profile/packages/resolver/test/evm.test.mjs).
  • Every exported ERC-7730 file in the consent tests is checked against the ERC-7730 2.1.0 JSON Schema (vendored, with its sha256), and the hashes and digests the tests pin were computed by an independent implementation.

A test against a contract would run on a local Anvil chain, as the examples on this page assume, never on mainnet.
