## 4. A lost reply, then a retry

Alice sends 0.29 TKA to Bob. The ledger runs the call, and the reply is lost on the way back (a dropped connection, simulated in the transport). The caller tries again two seconds later.

| Way | What the caller was told | Bob received | Transfers on the ledger |
|---|---|---|---|
| @icp-sdk/canisters `transfer({ to, amount })` (no created_at_time, the library's default) | error: network error: the connection dropped before the reply arrived; then retry: block 2 | 0.58 TKA | 2 |
| the same, with `created_at_time: now` set on each attempt | error: network error: the connection dropped before the reply arrived; then retry: block 4 | 0.58 TKA | 2 |
| the same, with one `created_at_time` kept for the retry | error: network error: the connection dropped before the reply arrived; then retry: error: IcrcTransferError Duplicate {"duplicate_of":"5"} | 0.29 TKA | 1 |
| @meantjs/tools: `prepare_icrc1_transfer`, confirm, `commit`, and `commit` again | commit: unknown; then prepare again: same preview (unknown); then commit again: already_done | 0.29 TKA | 1 |

- With the library's default (no `created_at_time`) or a new stamp per attempt, the ledger cannot tell the retry from a new payment: Bob is paid twice. With a kept stamp the ledger refuses the retry as a `Duplicate`, and the library throws it as an error: the money moved, the app is told it failed. Turning that `Duplicate` into "done" is left to each app.
- Meant's profile says it: `created_at_time` is the idempotency stamp, set once and reused, and `Err.Duplicate` is `already_done`. The tool layer sent the same bytes both times (2 sends, identical), and preparing the call again returned the same preview instead of a new stamp.
- Before each send the person was shown the preview: "Send tokens", 0.29 TKA to qohzy-wz6h5-aecqs-dircu-mr2ij-ffewt-cnjzh-vauks-knkfk-vsxlb-mqe, effect transfer, irreversible.
- @meantjs/reconcile read the ledger's ICRC-3 log afterwards and found the original transfer: `found`, block 6.

### Decimals: assumed by the app, or read from the ledger

| Way | Base units sent | Bob received (TKB, 6 decimals) |
|---|---|---|
| An app that converts with ICP's 8 decimals (`convertStringToE8s("1.5")` of @dfinity/utils) | 150000000 | ❌ 150 TKB |
| @meantjs/tools, decimals from the ledger's `icrc1_decimals`, as the profile names it | 1500000 | ✅ 1.5 TKB |

- The 8-decimal helper is an illustration of a known kind of bug, not a measurement of any app. The profile names where decimals come from (`{ "from": "query:icrc1_decimals" }`), and the host reads them from the canister: {"query:icrc1_decimals":6,"query:icrc1_symbol":"TKB"}.
- `1.5 TKA` given to the TKB ledger's tool was refused before any preview: `E_SYMBOL_MISMATCH`, the symbol "TKA" is not this token's symbol "TKB".

## 5. What an agent is told

The words an agent gets for the transfer's `amount`. Without a profile, all it has is the Candid type:

```
type TransferArg = record {
  from_subaccount : opt Subaccount;
  to : Account;
  amount : Tokens;
  fee : opt Tokens;
  memo : opt blob;
  created_at_time : opt Timestamp
};
```

With the ICRC-1 pack, from `toolDefinitions` of @meantjs/tools for the TKA ledger:

```
amount: Amount. Amount in TKA: a decimal number with at most 8 digits after the point, optionally followed by the symbol TKA. Digits on both sides of a point, no thousands separators or exponents. Never rounded: more digits after the point is an error, even zeros. For example "1", "1.25", "1.25 TKA".
pattern: ^\s*[0-9]+(?:\.[0-9]{1,8})?(?:\s+[Tt][Kk][Aa])?\s*$
```

- Whether these words make agents safer is what the preregistered eval tests; this run does not test any model.
