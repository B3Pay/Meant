# An example canister ready for ICP MCP

DFINITY's ICP MCP connector lets an assistant (Claude, ChatGPT and others) call a canister as the signed-in person.
Before it calls, it reads what the canister says about itself. This canister answers every one of those reads from
one Meant profile, so what the assistant is told cannot drift from what the canister means (D-061, step 2 of
`docs/proposals/w0-icp-mcp.md`).

| What an agent reads | Where it comes from |
|---|---|
| `candid:service` (custom section `icp:public candid:service`) | `icp-mcp.did`, embedded as it is |
| `candid:profile` (custom section `icp:public candid:profile`) | `icp-mcp.profile.json`, embedded as it is (spec §8.1) |
| `get_api_doc` | `api-doc.md`, written by `meant-profile api-doc` from the profile (spec §8.2) |
| `icrc21_canister_call_consent_message` | rendered at call time from `icp-mcp.resolved.json` by `meant-profile-consent` (the Rust port, byte for byte the JavaScript text) |
| `icrc10_supported_standards` | ICRC-10 and ICRC-21 |
| `/.well-known/ic-architecture` at the app's origin | `node manifest.mjs <canister id>` at deploy time |

The canister itself is TOK, a token with 8 decimals whose `send` is exactly-once. A send that carries `created_at`
is deduplicated for 24 hours on what it sends (caller, recipient, amount, memo and stamp, as ICRC-1 does), which is
what the guide tells an agent to rely on: send the same bytes again after a timeout, and an `Err.Duplicate` reply
means it already went through. What it remembers for that is bounded (`canister/src/token.rs`): a send of nothing is
refused, expired entries are dropped before each stamped send, and while 10,000 unexpired stamped sends are held a new
stamped send is refused with `Err.Other` until the oldest expire. The installer starts with 1,000 TOK. State is kept
in memory only; this is an example, not a ledger.

## Files

- `icp-mcp.did`, `icp-mcp.profile.json`: the interface and its author profile. Edit these.
- `icp-mcp.resolved.json`, `api-doc.md`: generated by `node build.mjs`; `scripts/icp-mcp-example.test.mjs` fails when
  they are not in step. Review the diff of `api-doc.md` like code: it is what agents are told.
- `canister/`: the Rust canister (no canister SDK; the system API directly, as the SNS validator example does). The
  token is `src/token.rs`, whose unit tests run on the host (`cargo test`). Its dependencies are exactly the consent
  crate's (`Cargo.lock` is the same tree plus this crate).
- `manifest.mjs`: the `ic-architecture` manifest, which opts the app into ICP MCP.

## Build and test

```sh
node examples/icp-mcp/build.mjs                    # after editing the .did or the profile
npm test                                           # includes scripts/icp-mcp-example.test.mjs
cd packages/consent/pocketic && npm ci && npm test # builds the wasm and runs it on PocketIC 16.0.0
```

The PocketIC test (`packages/consent/pocketic/test/icp-mcp.test.mjs`) checks that:
- the module's two custom sections are the `.did` and the profile, and the profile binds that `.did`;
- `get_api_doc` answers `api-doc.md`;
- every ICRC-21 reply is what `@meantjs/consent` answers for the same request, apart from the fields form, which the
  Rust crate refuses with `E_FORM`;
- a send moves tokens exactly once, and is refused with `TooOld`, `CreatedInFuture` or `Insufficient` as the profile
  classifies them.

## Deploy

```sh
cargo build --release --target wasm32-unknown-unknown --manifest-path examples/icp-mcp/canister/Cargo.toml
icp deploy   # or any tool that installs examples/icp-mcp/canister/target/wasm32-unknown-unknown/release/icp_mcp_example.wasm
node examples/icp-mcp/manifest.mjs <canister id> > dist/.well-known/ic-architecture
```

Publishing the manifest opts the app into ICP MCP and accepts DFINITY's ICP MCP App Operator Terms; read them first.
